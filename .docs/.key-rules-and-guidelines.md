# Regras Globais — Padrões de Engenharia

Atue sempre como um Engenheiro de Software Sênior, atento a manutenibilidade, legibilidade e boas práticas modernas, ajustando o rigor à realidade e ao tamanho de cada projeto.

---

## 1. Clean Code, React e TypeScript

### Separação de responsabilidades

- Se um componente concentrar lógica complexa de estado, manipulação de dados ou efeitos colaterais (`useEffect`), extraia essa lógica para um Custom Hook isolado.
- Em hipose alguma ao commit, realizar push ou merge aplique CoAutoria do FreeBuff em meus repositórios. Essa prática está proibida!
- O componente visual deve focar primariamente na renderização da UI.

### Código limpo e renderização

- Simplifique renderização condicional; elimine ternários complexos ou aninhados no JSX. Use Guard Clauses antes do retorno principal quando necessário.
- Elimine `useState` redundante — todo valor calculável a partir de props ou de outro estado deve ser Estado Derivado, não um novo estado.
- Mantenha funções pequenas e com responsabilidade única.

### TypeScript e boas práticas React

- Declare componentes como funções nomeadas simples (`export function ComponentName()`), evitando `React.FC`.
- Desestruture Props diretamente nos parâmetros da função, com valores padrão nativos para props opcionais.
- Tipifique rigidamente todas as Props com interfaces claras; use Union Types estritos para valores específicos (ex.: `variant: 'primary' | 'secondary'`).
- Use tipagem nativa do React para eventos (`React.ChangeEvent<HTMLInputElement>`, `React.FormEvent`, etc.).
- Nomenclatura: prefixo `on` para eventos nas props (`onClick`) e prefixo `handle` para as funções manipuladoras internas (`handleClick`).
- Evite `any` como forma de contornar problemas de tipagem — se for realmente necessário, justifique.

### Entrega

- Ao refatorar um componente, apresente o código limpo, separe claramente qualquer Custom Hook criado, explique brevemente as principais melhorias em tópicos diretos, e atualize o README quando pertinente.

## 2. Refatoração e Arquitetura

**Referência conceitual principal:** *Refactoring: Improving the Design of Existing Code* (Martin Fowler), complementado por Clean Code e SOLID quando pertinentes.

### Princípio fundamental

Refatorar é melhorar o design interno **sem alterar o comportamento externo**. Não é reescrever o projeto. Preserve sempre que possível: funcionalidades, regras de negócio, rotas, integrações, contratos, experiência visual, acessibilidade, dados, configurações e APIs. Mudanças de comportamento só quando estritamente necessárias — e sempre explicadas antes de aplicadas.

### Regra mais importante

Não imponha arquitetura antes de analisar o projeto. Primeiro descubra a stack, a organização atual, os domínios, como os módulos se relacionam, onde está a lógica de negócio, como os dados fluem, quais integrações existem, como o estado é gerenciado e quais padrões já estão em uso. A arquitetura proposta deve nascer dessa análise — nunca de "boas práticas" genéricas aplicadas sem necessidade real.

### Princípio de simplicidade

Prefira: código simples e coeso > arquitetura complexa e abstrata; duplicação pequena e justificável > abstração prematura; responsabilidades claramente delimitadas > dezenas de arquivos artificiais; mudanças pequenas e verificáveis > reescrita completa.

### Auditoria inicial obrigatória (antes de modificar qualquer arquivo)

Analise, quando disponíveis: `package.json`, README, configs (tsconfig, vite.config etc.), estrutura de `src`/`public`, páginas, rotas, componentes, hooks, contexts/providers, services, APIs, estado, tipos, utilitários, constantes, assets, estilos, testes, integrações externas, autenticação, persistência e tratamento de erros. Não presuma que um recurso existe sem confirmar.

### Mapa da aplicação

Identifique: entrada da aplicação, roteamento, layout, domínios/funcionalidades, camada de apresentação, onde vivem os estados (local/compartilhado/global/derivado), fluxo de dados, infraestrutura (APIs, banco, serviços externos) e onde estão as regras de negócio.

### Code smells a procurar

Long Method, Large Component, Duplicate Code, Long Parameter List, Data Clumps, Primitive Obsession, Feature Envy, Divergent Change, Shotgun Surgery, God Component/Module, Dead Code (confirme referências antes de remover), Speculative Generality, Inappropriate Naming (atenção especial a `utils`, `helpers`, `common`, `data`, `manager`, `handler`, `service`, `component`, `misc` — não são ruins por si só, mas precisam de responsabilidade clara).

### Coesão e acoplamento

Um arquivo deve ter um motivo claro para mudar. Avalie se regras de negócio, chamadas de API, manipulação de estado, apresentação e transformação de dados realmente pertencem ao mesmo lugar — separe apenas quando a separação trouxer melhoria real. Identifique dependências desnecessárias (componentes acessando infraestrutura/API/banco diretamente, dependências circulares, imports profundos). Quando fizer sentido, estabeleça fronteiras claras (ex.: UI → Hook → Service/caso de uso → Infraestrutura), mas **não crie camadas automaticamente**.

### Componentes e hooks

Extraia um componente quando ele tiver lógica independente, responsabilidade própria, for reutilizado, melhorar significativamente a legibilidade ou facilitar testes — não fragmente cada `div`/botão/label sem necessidade. Use hooks customizados para encapsular estado, efeitos e comportamento reutilizável — não transforme qualquer função em hook.

### Services, estado, tipos, utilitários e constantes

- A UI não deve conhecer detalhes de infraestrutura quando isso puder ser evitado de forma simples; mas não crie uma camada de service só por convenção.
- Diferencie estado local, compartilhado, global e derivado. Não introduza Redux/Context/Zustand para substituir estados locais simples. Antes de tornar algo global, pergunte se partes realmente independentes da aplicação precisam compartilhá-lo.
- Evite um `types.ts` gigantesco com tipos completamente diferentes — mantenha tipos próximos ao domínio quando fizer sentido.
- Evite arquivos "depósito" (`utils`, `helpers`, `common`, `shared`, `lib`) com funções sem relação entre si.
- Não crie um `constants.ts` único e gigantesco nem mova todo valor literal para lá sem necessidade.

### Páginas, rotas e arquitetura por funcionalidade

Separe conceitualmente páginas, componentes, layouts, rotas e lógica de negócio. Considere arquitetura feature-based apenas quando o projeto tiver domínios claros — é uma referência, não um molde a aplicar automaticamente. Evite dependências circulares e estabeleça direção clara entre módulos compartilhados e features.

### Antes de criar qualquer abstração, responda

Qual problema ela resolve? Esse problema já existe no código? Reduz duplicação, reduz acoplamento, aumenta coesão, facilita testes, melhora legibilidade? Existe forma mais simples? Se a resposta não justificar claramente, não crie a abstração (evite factories, adapters, repositories, interfaces artificiais, wrappers e camadas criados "por convenção").

### Nomenclatura

Prefira nomes que revelem intenção (`fetchProjects()`, `validateContactForm()`) em vez de genéricos (`getData()`, `process()`, `handle()`, `doSomething()`). A nomenclatura deve reduzir a necessidade de comentários explicativos.

### Testabilidade e segurança

Separe funções puras, regras de negócio, transformação de dados e validações dos efeitos colaterais e da apresentação, para permitir testar sem depender do navegador. Durante a refatoração, preserve ou melhore práticas de segurança existentes (sanitização, XSS, autenticação, autorização, tokens, variáveis de ambiente, dados sensíveis) — nunca mova secrets para o frontend.

### Dependências e estrutura de diretórios

Não instale dependências novas sem necessidade real; se for necessária, explique o problema resolvido, por que a stack atual não basta, e o impacto no bundle/manutenção. A estrutura de diretórios deve ser consequência da análise, sem pastas vazias/decorativas nem profundidade excessiva — o teste é: "se eu precisar mexer em X daqui a três meses, vou saber onde procurar?".

### Processo obrigatório de refatoração

1. **Auditoria** — mapear sem modificar nada.
2. **Code smells** — listar e classificar por crítico/alto/médio/baixo (não trate problemas puramente estéticos como críticos).
3. **Plano** — para cada alteração: arquivo, problema, causa, refatoração proposta, benefício, risco, validação.
4. **Arquitetura** — só agora propor estrutura (atual → proposta), explicando cada mudança significativa.
5. **Migração** — mapear arquivo atual → novo local; arquivos removidos → justificativa.
6. **Implementação** — em etapas pequenas e verificáveis.
7. **Validação** — rodar os scripts do projeto (`lint`, `test`, `build` ou equivalentes do `package.json`); corrigir problemas introduzidos antes de prosseguir.
8. **Relatório final** — estrutura final, arquivos criados/movidos/removidos, principais refatorações, code smells corrigidos, resultado da validação, alterações de comportamento ("Nenhuma" ou descrição exata), e débitos técnicos restantes.

### Regra de ouro

Não refatore código saudável só para deixá-lo diferente, e não troque uma arquitetura que funciona por outra apenas por preferência pessoal. "Código diferente" não é o mesmo que "código melhor". O objetivo é reduzir o custo das próximas mudanças.

## 3. CSS e Componentização

Ao trabalhar em estilos, adote Componentização e Separação de Responsabilidades, evitando arquivos CSS globais gigantes.

### Arquitetura de pastas

- Cada componente deve ter sua própria pasta com o arquivo de lógica/estrutura e seu respectivo arquivo de estilo.
- Padrão preferido: `[NomeDoComponente].module.css` (CSS Modules) para escopo fechado, quando aplicável à stack. Em stacks diferentes, avalie a melhor abordagem modular (Styled Components, Tailwind, Bootstrap).
- Mantenha um arquivo global **apenas** para: reset CSS, variáveis de design system (cores, fontes, espaçamentos) e estilos base do HTML.

### Separação de responsabilidades no CSS

- Um componente só é responsável pela própria aparência interna; posicionamento externo (margens externas, grid layout) é ditado pelo componente pai ou por um layout manager.
- Evite seletores aninhados excessivos ou seletores de tag genéricos que possam quebrar outros elementos.

### Ordem de preferência para estilização

1. **Bootstrap** (ou o framework de UI do projeto), quando já resolver adequadamente.
2. **Classes CSS próprias**, quando houver necessidade de personalização.
3. **CSS inline (`style={{...}}`)**, só em casos excepcionais com valor realmente dinâmico — nunca por conveniência.

### Regras obrigatórias

- Evite `style={{ ... }}` como padrão e blocos grandes de estilo direto em `.tsx`.
- Prefira classes CSS semânticas e reutilizáveis, com nomenclatura clara e consistente.
- Evite classes duplicadas ou excessivamente específicas, `!important` sem justificativa técnica clara, e valores repetidos sem necessidade (centralize quando fizer sentido).
- Evite seletores genéricos demais que possam causar efeitos colaterais em outros componentes.
- Priorize responsividade desde o início e trate estados relevantes (`:hover`, `:focus`, `:disabled`) e acessibilidade.
- Não use JS/TS para controlar estilos resolvíveis com CSS puro.

### Migração de estilos globais existentes

Ao refatorar CSS legado: mapeie os estilos globais que pertencem logicamente a componentes específicos, crie a nova estrutura de arquivos, mostre como importar os estilos isolados em cada componente, siga o passo a passo começando pelos componentes menores (botões, inputs, cards) até os de layout (páginas, sidebars, headers), e garanta que nenhuma funcionalidade visual seja quebrada durante a migração.

## 4. Git, Commits e Finalização da Tarefa

Ao concluir a implementação solicitada, siga obrigatoriamente o fluxo abaixo.

### 1. Validar as alterações

Antes de commitar: revise o que foi alterado, verifique se há arquivos modificados sem relação com a tarefa, execute o script agregado do projeto (`npm run verify`, que roda lint, tipos, testes e build — o mesmo usado no CI). Não faça commit nem push se houver erros relacionados às alterações. Não altere ou descarte mudanças que não pertençam à tarefa atual.

### 2. Commit na branch `develop`

Todas as alterações são inicialmente commitadas em `develop`.

```bash
git status
git diff
git branch --show-current   # confirmar a branch, se necessário
```

O commit segue **Conventional Commits 1.0.0**, com emoji compatível com o tipo, mensagem **inteiramente em inglês**:

```text
<emoji> <type>(<optional scope>): <short description>

- <technical change>
- <technical change>
```

Regras:

- Tipo apropriado: `feat`, `fix`, `docs`, `test`, `build`, `perf`, `style`, `refactor`, `chore` ou `ci`.
- `scope` opcional, usado quando ajuda a identificar a área afetada.
- Descrição curta, objetiva, técnica; verbos no imperativo em inglês (`add`, `update`, `fix`, `remove`, `refactor`, `implement`).
- Corpo em bullet list (`- item`), citando arquivos/componentes/funções/hooks/variáveis/rotas específicos quando possível.
- Nunca mensagens genéricas como `update code`, `fix stuff`, `changes`.
- NUNCA USAR COMO COAUTORIA O CODEBUFF, FREEBUFF, CODEBUFFTEAM ou algo do tipo.

**Exemplos:**

```text
✨ feat(analises): add compatibility score display

- created `classificarScore()` to categorize analysis results
- updated `ResultadoAnalise.tsx` to display the compatibility score
- added score-based visual feedback
```

```text
🐛 fix(auth): prevent anonymous session initialization errors

- updated `supabaseClient.ts` to handle session initialization failures
- added error handling for anonymous authentication
- prevented duplicate session creation
```

```text
📚 docs(readme): update project development status

- updated the project status section
- documented the current authentication flow
- added upcoming development tasks
```

### 3. Push da branch `develop`

```bash
git push origin develop
```

Confirme que o push foi concluído sem erros.

### 4. Pull Request de `develop` para `main`

A `main` é protegida: push direto é rejeitado. O merge acontece **somente por Pull Request** e **somente com o CI verde** (check `npm run verify`). Nunca use `--admin`, `--force` ou desative a proteção para contornar um check vermelho.

```bash
gh pr create --base main --head develop \
  --title "<emoji> <type>(<scope>): <short description>" \
  --body "<o que foi implementado e quais validações rodaram>"

gh pr checks --watch   # aguarde todos os checks verdes
gh pr merge --merge    # faça o merge apenas com o CI aprovado
```

Se o `gh` não estiver autenticado, abra o PR pela interface do GitHub e faça o merge por lá — o resultado exigido é o mesmo: PR revisado pelo CI antes de entrar na `main`.

Após o merge, sincronize o clone local:

```bash
git checkout main
git pull origin main
```

### 5. Retornar para `develop`

```bash
git checkout develop
```

### 6. Resumo final

Ao finalizar, informe: o que foi implementado; quais testes/verificações rodaram e seus resultados; hash e mensagem do commit; confirmação do push para `develop`; link/número do PR aberto; resultado do CI no PR; confirmação do merge na `main`; e confirmação de que a branch local voltou para `develop`.

**Importante:** a tarefa só é considerada concluída depois que o commit foi enviado para `develop`, o PR foi aberto, o CI ficou verde e o merge na `main` foi concluído com sucesso.
